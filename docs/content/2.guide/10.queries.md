# GET queries with Nuxt

Use a `.get.ts` action for reads, and compose it with Nuxt's existing `useAsyncData` for SSR payload reuse, refresh, and hydration. The module does not introduce a separate cache.

```ts [server/actions/get-stats.get.ts]
import { createSafeActionClient } from '#safe-action'

export default createSafeActionClient().action(() => ({ status: 'ready' }))
```

```vue
<script setup lang="ts">
import { getStats } from '#safe-action/actions'

// During SSR, forward only the headers the action needs. On the client this is {}.
const headers = useRequestHeaders(['cookie'])
const action = useAction(getStats, { headers })

const { data, error, status, refresh } = await useAsyncData('action:stats', async () => {
  const result = await action.executeAsync(undefined)
  if (result.serverError !== undefined || result.validationErrors !== undefined) {
    throw createError({ statusCode: 500, statusMessage: 'Unable to load stats' })
  }
  // This read action returns an object; useAsyncData handlers should return defined data.
  if (result.data === undefined) throw createError({ statusCode: 500, statusMessage: 'Missing stats' })
  return result.data
})
</script>

<template>
  <p v-if="status === 'pending'">Loading…</p>
  <p v-else-if="error" role="alert">Unable to load stats</p>
  <p v-else>{{ data?.status }}</p>
  <button @click="refresh()">Refresh</button>
</template>
```

The example is an unauthenticated read, but the allowlisted cookie-forwarding pattern also applies to authenticated actions. Server-side global `$fetch` does not automatically forward the current browser request's cookies. Do not forward all incoming headers wholesale. Use the default transport on the server; detached browser fetch cannot resolve a relative URL in every server runtime.

For input-dependent reads, include stable serialized input in the `useAsyncData` key or use Nuxt's reactive key/watch options. Return only defined successful data. A void mutation is not a useful query handler. Nuxt owns the cached query data; `useAction` state is execution-local and is not hydrated query state.

Keep mutations POST/PUT/PATCH/DELETE and refresh relevant Nuxt keys after success. This module disables automatic transport retries; application retry policy and idempotency remain explicit.

[Nuxt useAsyncData](https://nuxt.com/docs/4.x/api/composables/use-async-data) · [Nuxt request headers](https://nuxt.com/docs/4.x/api/composables/use-request-headers)

## Refresh after a mutation

Register tags against an ordinary explicit Nuxt data key, then request invalidation from the mutation:

```ts
const key = 'profile:summary'
useActionQueryTags(key, ['profiles'])
const { data } = await useAsyncData(key, readSummary)
const mutation = useAction(updateProfile, {
  invalidate: { keys: ['profile:summary'], tags: ['profiles'] },
})
```

`useActionQueryTags(key, tags)` returns an unregister function and registers ownership in the current Nuxt app. Vue scope disposal unregisters its own registration. Multiple owners may register the same key; one scope's disposal does not remove another owner's entry. Tags are app-scoped rather than shared between SSR requests. Unregistered tags match no keys; explicit keys still work. Matching keys are deduplicated.

Nuxt owns fetch, payload reuse, SSR hydration, and caching. This helper maps tags to keys; it does not fetch data or invalidate arbitrary API routes. Call it in setup with a stable explicit key; for changing keys/tags, unregister and register the new pair.

Only successful latest mutations trigger refresh. Expected business failures, validation failures, transport/server errors, cancellation and stale executions do not. While refresh is pending, `isRefreshing` is true. If refresh rejects, `refreshError` is separate from mutation errors and the mutation remains successful. It cannot undo a completed write.

The [runnable profile example](https://github.com/rutbergphilip/nuxt-safe-action/tree/main/example) demonstrates a tagged ordinary `useAsyncData` counter refreshed after acceptance.

During SSR, Nuxt's `refreshNuxtData()` is a no-op. Normal query handler failures are captured by the query's `error` ref, so they can occur even when the refresh trigger resolves. Display the query error separately; `refreshError` covers a rejected trigger/hook. Cancelling an action after refresh has started does not abort the independent Nuxt fetch.
