# Queries

Use a `.get.ts` action for reads and load it with `useActionQuery`. It wraps Nuxt's `useAsyncData`, so SSR payload reuse, hydration, `refresh`, `refreshNuxtData` and `clearNuxtData` behave as Nuxt documents. The module adds no separate cache.

```ts [server/actions/get-project.get.ts]
import { z } from 'zod'
import { createSafeActionClient } from '#safe-action'

export default createSafeActionClient()
  .schema(z.object({ id: z.string() }))
  .errors({ NOT_FOUND: 'Project not found' })
  .action(async ({ parsedInput, fail }) => {
    const project = await db.projects.find(parsedInput.id)
    if (!project) fail('NOT_FOUND')
    return project
  })
```

```vue
<script setup lang="ts">
import { getProject } from '#safe-action/actions'

const route = useRoute()
const { data, businessError, status, refresh } = await useActionQuery(
  getProject,
  () => ({ id: String(route.params.id) }),
  { tags: ['projects'] },
)
</script>

<template>
  <p v-if="status === 'pending'">Loading…</p>
  <p v-else-if="businessError?.code === 'NOT_FOUND'">No such project</p>
  <h1 v-else>{{ data?.name }}</h1>
  <button @click="refresh()">Refresh</button>
</template>
```

- **Typed results.** `data`, `businessError`, `validationErrors`, `serverError` and `clientError` keep the action's types. `data` is `undefined` (never `null`) until a successful result arrives, on every Nuxt version.
- **Status.** `status` is Nuxt's status, except that a settled result carrying any error reports `'error'`. Action failures never throw; Nuxt's own `error` ref only holds failures of the data layer itself.
- **Per-input keys.** The key is `safe-action:<action path>:<hash of the input>`. Inputs that are equal after sorting object keys share an entry. On Nuxt 3.17 and newer the key is reactive: changing the input fetches a new entry and aborts the superseded request. On Nuxt 3.8–3.16 the key stays fixed at setup and an input change refetches under it. Nuxt drops entries nothing uses, so returning to an earlier input fetches it again. Pass `key` to choose your own.
- **SSR authentication.** During SSR the `cookie` request header is forwarded to the action, so the signed-in user is seen on the first render. Change the allowlist with `forwardHeaders: ['cookie', 'authorization']`, or disable it with `forwardHeaders: false`. Incoming headers are never forwarded wholesale, and nothing is forwarded from the browser.
- **Nuxt options.** `server`, `lazy`, `immediate` and `dedupe` are passed through to `useAsyncData`. `headers`, `credentials` and `timeout` apply to the request. Transport retries stay disabled.

The return value is awaitable like `useAsyncData`. Use `lazy: true` without `await` to render before data arrives.

### Without `useActionQuery`

You can still compose `useAction` with `useAsyncData` yourself, for example to transform the result before caching it. Forward only the headers the action needs with `useRequestHeaders(['cookie'])`; server-side global `$fetch` does not forward the browser request's cookies. Include stable serialized input in the key and return only defined successful data from the handler.

[Nuxt useAsyncData](https://nuxt.com/docs/4.x/api/composables/use-async-data) · [Nuxt request headers](https://nuxt.com/docs/4.x/api/composables/use-request-headers) · [`useActionQuery` reference](/api/use-action-query)

## Refresh after a mutation

Give a query `tags`, then name those tags in a mutation's `invalidate` option:

```ts
const projects = await useActionQuery(listProjects, undefined, { tags: ['projects'] })
const rename = useAction(renameProject, { invalidate: { tags: ['projects'] } })
```

`useActionQuery` registers its tags against its current key, moves them when the input changes, and releases them when the component unmounts.

For your own `useAsyncData` or `useFetch` calls, register tags against an explicit Nuxt data key:

```ts
const key = 'profile:summary'
useActionQueryTags(key, ['profiles'])
const { data } = await useAsyncData(key, readSummary)
const mutation = useAction(updateProfile, {
  invalidate: { keys: ['profile:summary'], tags: ['profiles'] },
})
```

`useActionQueryTags(key, tags)` returns an unregister function and registers ownership in the current Nuxt app. Vue scope disposal unregisters its own registration. Multiple owners may register the same key; one scope's disposal does not remove another owner's entry. Tags are app-scoped rather than shared between SSR requests. Unregistered tags match no keys; explicit keys still work. Matching keys are deduplicated.

Nuxt owns fetch, payload reuse, SSR hydration, and caching. This helper maps tags to keys; it does not fetch data or invalidate arbitrary API routes. Call it in setup with a stable explicit key; for changing keys/tags, unregister and register the new pair.

Only successful latest mutations trigger refresh. Expected business failures, validation failures, transport/server errors, cancellation and stale executions do not. While refresh is pending, `isRefreshing` is true. If refresh rejects, `refreshError` is separate from mutation errors and the mutation remains successful. It cannot undo a completed write.

The [runnable profile example](https://github.com/rutbergphilip/nuxt-safe-action/tree/main/example) demonstrates a tagged ordinary `useAsyncData` counter refreshed after acceptance.

During SSR, Nuxt's `refreshNuxtData()` is a no-op. Normal query handler failures are captured by the query's `error` ref, so they can occur even when the refresh trigger resolves. Display the query error separately; `refreshError` covers a rejected trigger/hook. Cancelling an action after refresh has started does not abort the independent Nuxt fetch.
