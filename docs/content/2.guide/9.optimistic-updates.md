# Optimistic updates

`useOptimisticAction` extends `useAction`. Provide a writable `currentData` ref and an immutable `updateFn(input, current)` that returns a new value. It changes `currentData` immediately and exposes a readonly `optimisticData` view.

```vue
<script setup lang="ts">
import { ref } from 'vue'
import { toggleTask } from '#safe-action/actions'

const tasks = ref([{ id: '1', title: 'Try server actions', done: false }])
const { execute, optimisticData, isExecuting, serverError, cancel } = useOptimisticAction(toggleTask, {
  currentData: tasks,
  // Toggling task 1 and then task 2 keeps both requests and both updates.
  mode: 'merge',
  updateFn(input, current) {
    return current.map(task => task.id === input.id ? { ...task, done: input.done } : task)
  },
})
</script>

<template>
  <ul>
    <li v-for="task in optimisticData" :key="task.id">
      <button @click="execute({ id: task.id, done: !task.done })">
        {{ task.done ? '✓' : '○' }} {{ task.title }}
      </button>
    </li>
  </ul>
  <p v-if="isExecuting">Saving…</p>
  <p v-if="serverError" role="alert">{{ serverError }}</p>
  <button type="button" @click="cancel()">Cancel pending updates</button>
</template>
```

Use this demonstration action for that example. It validates and echoes a desired state; connect real storage and authorization in your application.

```ts [server/actions/toggle-task.ts]
import { z } from 'zod'
import { createSafeActionClient } from '#safe-action'

export default createSafeActionClient()
  .schema(z.object({ id: z.string().min(1), done: z.boolean() }))
  .outputSchema(z.object({ id: z.string(), done: z.boolean() }))
  .action(({ parsedInput }) => parsedInput)
```

## Concurrency: `replace` vs `merge`

`mode` controls what happens when you execute again while an earlier mutation is still in flight.

| `mode` | Earlier request | Optimistic view | Use for |
|---|---|---|---|
| `'replace'` (default) | Aborted | Earlier update rolled back; the newer update is applied to the restored baseline | One value that each call fully supersedes, e.g. a search filter or a single setting |
| `'merge'` | Keeps running | Every pending update stays applied, in call order | Independent changes, e.g. toggling different list items |

In `replace` mode only one optimistic operation is owned at a time. Starting a newer execution cancels the earlier request, restores its baseline when still owned, and applies the new update to current authoritative data. This is **replacement**, not a queue of accumulating changes. Because the earlier request is aborted on the client after the server may already have committed it, `replace` can briefly show a state the server does not have when the calls touch different data — use `merge` there.

In `merge` mode the helper keeps a confirmed base value and an ordered list of pending updates; `currentData` is the base with every pending update applied. When an execution succeeds its update becomes part of the base. When one fails or is aborted, only that update is removed and later updates are replayed with `updateFn` on top of what remains, so `updateFn` must be pure. `cancel()` and `reset()` abort every request and roll back every update that has not succeeded yet. As in `useAction`, reactive state (`status`, `data`, `serverError`, …) and the `onSuccess`/`onError`/`onSettled` callbacks belong to the latest execution; await `executeAsync` to observe each call's own result. Passing `cancelPrevious: true` with `merge` aborts and rolls back the earlier execution.

## Ownership and reconciliation

Failure/cancel/reset rolls back only if `currentData.value` is still the same value the helper installed. Replacing the ref during an external refresh prevents an older rollback from undoing that refresh. In `merge` mode an external replacement while updates are pending becomes the new authoritative value and releases all of them: later completions no longer change `currentData`. Reconcile after the pending work settles (or with a Nuxt data refresh) rather than writing `currentData` from `onSuccess`. This identity guard does not detect in-place external edits; replace values and keep `updateFn` immutable.

On success, the optimistic value remains until your application reconciles it. The helper never assigns arbitrary action output to `currentData`; output may be a different shape. Use `onSuccess` or await `executeAsync` to merge a response or refresh a Nuxt query. Async callbacks are not awaited. Server mutations may still complete after client cancellation; refresh authoritative data where that distinction matters.

All `useAction` options apply. `cancel()` and `reset()` also release the helper's owned optimistic change. [API reference](/api/use-optimistic-action).

If `updateFn` throws, no request starts; `executeAsync` rejects and `execute` logs the failure. Keep `updateFn` pure and immutable.
