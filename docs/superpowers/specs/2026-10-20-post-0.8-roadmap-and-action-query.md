# Post-0.8 roadmap and `useActionQuery` design

Date: 2026-10-20 · Status: accepted (decided by maintainer delegation) · Target: 0.9.0

## 1. Order of the four missing capabilities

| # | Capability | Why this position |
|---|---|---|
| 1 | **Query layer (`useActionQuery`)** | Every app reads data, not just some. Today a typed read takes ~15 lines of `useAction` + `useAsyncData` + manual error unwrapping + manual cookie forwarding (see `docs/content/2.guide/10.queries.md`). nuxt-actions computes its cache key once at setup, so per-input caching is likely broken there; doing it correctly is a concrete, demonstrable win. It also completes our existing tag invalidation, which currently needs hand-registered keys. |
| 2 | **File uploads** | Second most common need in CRUD/SaaS apps (avatars, attachments). Needs a deliberate CSRF design because 0.8 requires same-origin JSON for non-GET. nuxt-actions has no size/type limits, so "safe uploads" is our angle. |
| 3 | **SSE streaming** | Mostly AI/chat features; a narrower audience, and users can fall back to a plain Nitro route today. |
| 4 | **OpenAPI** | Matters mainly for teams with non-Nuxt clients, who are not the core audience of a Nuxt server-actions module. |

Infinite/paginated queries are a follow-up to #1 (0.9.x), built on the same key and payload model.
Each item gets its own spec, plan and PR.

## 2. `useActionQuery` — problem

A developer building a dashboard wants: typed data from an action, SSR + hydration without a double fetch,
a refetch when the input changes, a cache entry per input, the signed-in user's cookie forwarded during SSR,
typed business/validation errors, and a refresh after a mutation. Today each of those is manual.

## 3. Proposed API

```ts
const { data, businessError, validationErrors, serverError, clientError,
        status, pending, hasErrored, result, refresh, execute, clear, key } =
  await useActionQuery(getProject, () => ({ id: route.params.id }), {
    tags: ['projects'],           // registered for useAction({ invalidate: { tags } })
    forwardHeaders: ['cookie'],   // default; false disables; SSR only
    // passthrough to useAsyncData: server, lazy, immediate, dedupe
    // passthrough to the transport: headers, credentials, timeout
    // key: override the generated key (string or getter)
  })
```

- `input` is `MaybeRefOrGetter<TInput>`; it may be omitted for void-input actions.
- The return value is awaitable (like `useAsyncData`) and usable without `await` with `lazy: true`.
- Works with any HTTP method; GET actions are recommended for reads.

## 4. Behaviour

- **Storage.** `useAsyncData` stores the whole action envelope (`ActionResult`), so SSR payload,
  hydration, `getCachedData`, `refreshNuxtData` and `clearNuxtData` all behave as Nuxt documents.
  `data`, `serverError`, `businessError`, `validationErrors` and `clientError` are computed from it,
  keeping per-action error types. `data` is `undefined` (never `null`) on every Nuxt version.
- **Status.** `status` is Nuxt's status, except a settled envelope that carries any error reports `'error'`.
  `hasErrored` mirrors that. Nuxt's own `error` ref is still exposed for handler-level failures.
- **Key.** Default key: `safe-action:<path>` plus `:<hash>` of a stable (key-sorted) JSON serialization
  of the input. The hash keeps the payload small; objects with the same content in a different key
  order share an entry.
- **Reactivity.** On Nuxt ≥ 3.17 (reactive `useAsyncData` keys), the key is a computed, so every input
  gets its own payload entry: SSR hydration, `refreshNuxtData(key)` and tags address exact inputs and
  different inputs never overwrite each other. On Nuxt 3.8–3.16 the key is
  fixed at setup and input changes trigger a refetch via `watch` (correct data, one entry).
  Nuxt purges keys nobody uses, so returning to an earlier input refetches it; a client-side
  stale-while-revalidate cache is a separate follow-up, not part of this API. The module
  writes the detected capability to a build template, so there is no runtime sniffing.
- **Cancellation.** The `AbortSignal` Nuxt passes to the handler (Nuxt ≥ 3.17) is forwarded to the
  request, so superseded fetches are aborted on the wire.
- **SSR auth.** On the server, the allowlisted request headers (default `['cookie']`) are forwarded
  through `useRequestHeaders`. Nothing is forwarded on the client. Headers are never forwarded wholesale.
- **Tags.** `tags` are registered against the current key and re-registered when the key changes;
  registrations are released when the scope is disposed. `useAction(..., { invalidate: { tags } })`
  then refreshes the query through the existing success-only path.
- **Transport.** Reuses `useAction` request semantics: no automatic retries, typed `clientError`,
  `serverError` populated from transport failures for compatibility.

## 5. Compatibility

Purely additive: a new auto-imported composable, a new build template, new exported types.
No change to `useAction`, `useActionQueryTags`, handler or wire format. Nuxt support stays `>=3.8.0`.

## 6. Out of scope (this PR)

Stale-while-revalidate/stale-time caching, infinite queries, `prefetchAction`, `useActionMutation` sugar, polling, retries, stale-time.

## 7. Verification

- Unit tests (mocked `#app`): key generation and stability, envelope → refs mapping, status mapping,
  signal forwarding, header forwarding on server only, tag registration/re-registration/release,
  fallback mode on old Nuxt, awaitability.
- E2E (basic fixture): SSR-rendered page using `useActionQuery` against a GET action, asserting the
  data is in the HTML and the payload, a business error rendered from SSR, and a cookie forwarded
  to an action that reads it.
- Full `pnpm verify` equivalent: lint, typecheck, tests, prepack, package smoke.
